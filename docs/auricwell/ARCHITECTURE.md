# AuricWell: one backend, two frontends

User clarification, September 29, 2026: AuricWell is the branded, expandable EHR frontend for the existing platform. The existing frontend remains the full suite. Both use one functioning backend with shared clinical and financial services and canonical records.

## Required boundary

- Keep the independent AuricWell Vue frontend and branding.
- Use the existing organization, patient, provider, appointment, clinical documentation, Note Aid and billing domain services/models. Extract reusable services from coupled controllers where necessary; avoid copying their business rules into a second implementation.
- Resolve an authorized organization, actor, product and capability context at the backend boundary. Shared services must enforce that context for reads, writes, workers, downloads, search and caches. Shared infrastructure does not authorize cross-practice record access.
- Preserve separately scoped AuricWell credentials/sessions and the existing full-suite login/SSO behavior. Product login differences do not require parallel clinical or billing data stores.
- Keep product-specific branding, capabilities, onboarding progress and contracting configuration where needed. Build genuinely missing clinical/financial functionality in the shared domain layer so both frontends can use it when authorized.
- Isolate school, payroll, hiring and other full-suite side effects through explicit backend capabilities and workflow options. Hiding navigation is insufficient.
- A `/api/auricwell` namespace may adapt authentication and response presentation, but must delegate clinical and financial work to shared services.

## Note Aid direction confirmed

The established clinical writer and its interface are the reference, not a candidate for replacement. Both frontends open the documentation workspace with drafts on the left and to-do/supervision on the right. Selecting a note collapses both panels, including subsequent draft switches; users can reopen either panel. AuricWell uses its white interface, simple logo and blue controls. Supervision tasks must be assigned to the current supervisor and signatures remain exact-version backend actions.

The base clinical prompt builder and tool-specific model/token settings now live in `clinicalNoteWriter.service.js`, used by the existing generator and AuricWell. Existing prompts, transcript-fidelity instructions, full-suite context assembly and post-processing remain intact. AuricWell passes only its authorized facts and requires configured private AI transport; it uses the existing section parser and incomplete-intake validation. This is a shared writer foundation, not complete Note Aid parity: canonical draft/note storage, chart history, questionnaires, treatment-plan context, catalog overrides and the remaining established editor capabilities still need scoped adapters. Do not replace those workflows with independently designed alternatives.

“Financial workflows” means the EHR revenue cycle: insurance/eligibility, claims, payments/refunds, patient responsibility and reconciliation. Reuse the existing billing domain and preserve reviewed submission/uncertainty controls. AuricWell subscription charges remain separate; payroll and provider employment are outside scope.

## Consolidation progress

The first implementation step now connects new AuricWell practices to `agencies` through the existing Agency model. New patient demographics use `clients` through the existing Client model and the shared `clientChart.service.js`. Manual chart creation, reviewed intake and patient/billing imports all follow that path. AuricWell patient records retain stable public IDs, access/provenance metadata and a foreign-key link; they do not maintain a second active copy of name, birth date, phone, email, address or status.

Reads resolve the client through its owning agency. AuricWell edits require the shared-row fingerprint, preventing an older AuricWell view from overwriting intervening full-suite edits. Updates and product-link creation are transactional. Existing shared status values and structured addresses are preserved when the corresponding displayed field is unchanged. Existing full-suite Client/Agency call defaults remain in place.

Prototype charts remain readable. Operator-only, exact-preview consolidation can create canonical charts or explicitly link reviewed existing clients. It preserves chart IDs and note references, archives the original prototype snapshot and leaves an existing shared client's demographics unchanged. Matching names never establish identity. Retries are idempotent. Shared charts are retained during import rollback rather than archived or terminated automatically.

Existing staff identities can now be explicitly connected through an operator-reviewed preview in Settings. The connection uses `users` and `user_agencies`, retains the AuricWell account/provider IDs, archives the prior provider snapshot and reads the display name from the shared user. It does not create or modify full-suite credentials, roles, memberships, employment status or login sessions. No name/email matching is automatic. Identity links are unique and immutable, and changed previews are rejected. Pending accounts stay pending.

Linked providers require a fresh clinical credential review. Changes to the shared credential invalidate that review; shared or AuricWell access revocation blocks new scheduling, Note Aid and signing eligibility. Historical records remain readable to authorized practice users. Shared user reads are agency-scoped, exclude authentication secrets and are locked during transactional clinical decisions. An identity link does not establish payer enrollment, supervision or billing eligibility.

New owners, manually added staff and reviewed staff imports now create canonical `users` and `user_agencies` records transactionally. These identities have `identity_product=auricwell_ehr`, an `EHR_ONLY` status and no full-suite password. Product account activation, MFA and permissions remain in AuricWell. Full-suite JWT issuance, authentication and password/recovery paths reject these identities; existing users retain the full-suite default. Practice administrators can edit new staff names and professional credentials through Settings, with shared-row version checks. Credential changes require renewed clinical mapping review. Existing full-suite identities retain their existing profile workflow; multi-practice editing/connection remains held for a dedicated review flow.

New appointments now use the existing Appointment model and shared `appointmentRecord.service.js`. The adapter retains product IDs, series metadata and chart/provider references, while time, status, modality, location and service code come from canonical `appointments` and `appointment_participants`. Individual edits require both product revision and shared-row fingerprint; reviewed series previews include shared versions. Patient/provider conflicts include canonical visits, and failed product links roll back the shared appointment. Changed shared patient/provider assignments fail closed pending review. Prototype appointments remain readable but read-only until an explicit conversion workflow is implemented.

EHR-origin appointments do not enter full-suite email/SMS reminders, reply actions, automatic clinical-session linking or settlement. Dispatchers recheck the origin even if a reminder was accidentally queued. Existing full-suite update/cancel/settle orchestration directs EHR-origin visits back to their EHR workspace until shared clinical and financial orchestration is connected. This is shared appointment persistence, not complete cross-frontend workflow acceptance. Canonical conflicts serialize through the shared record service; concurrent legacy writers that bypass it still need end-to-end verification.

Primary/subscriber insurance review now uses the existing encrypted `clients.billing_insurance_payload` through `clientInsurance.service.js`. AuricWell retains review/provenance metadata rather than a second active coverage copy. Reads use the chart's owning agency; saves require a fingerprint spanning current shared coverage and product review. Shared secondary coverage and intake-profile provenance survive primary-policy edits. Earlier prototype coverage requires explicit comparison and is archived before conversion. Claim preview/approval/submission includes the shared insurance fingerprint, so shared edits invalidate older approvals before transmission.

The Insurance claims workspace now delegates to the shared Claim.MD workspace/workflow controllers. The adapter resolves the practice's canonical agency and active staff identity and checks product billing permission/capability/PHI gates before issuing a request-local, practice-bound financial capability. Object identity prevents request fields or cloned users from forging this grant; full-suite billing permissions and provider restrictions remain unchanged. It narrows even superadministrator queries to the owning practice; no role is elevated. Shared claim IDs, notes, encounters, approval hashes, duplicate prevention and audit history remain authoritative. Both frontends use the same claim review component and optional provider/payer transition policy. The AuricWell transport keeps its own session and rejects ERA enrollment changes while remittances remain with TherapyNotes. Earlier product claims remain separate for follow-up; no automatic conversion or duplicate claim ledger is introduced. See [billing rollout](../billing/claimmd-rollout.md).

**The full architecture correction is not complete.** Multi-practice identities, care-team assignments, shared clinical/billing provider profiles, prototype appointment conversion, clinical notes, Note Aid orchestration and remaining financial workflows still require consolidation. Shared insurance and claim review/submission are connected; AuricWell's separate note editor does not yet create the canonical signed note/encounter needed by the shared queue. Secondary-policy editing, authorization utilization and the wider revenue cycle remain incomplete. These domains remain on prototype paths except for the canonical records described above. Full-suite UI concurrency/version handling and background side effects still need complete end-to-end validation. New-practice production commissioning remains held for that remaining work; new practices do not need a pre-existing full-suite login.

New canonical clinical organizations are created inactive. Connecting records does not commission the full-suite modules, grant login/membership access, send invitations or enable background billing. Production activation remains held until the remaining shared-domain and capability work is complete.

## Next implementation priority

Consolidation precedes further parallel EHR feature development. Map the domain records and identity references, establish the shared product/organization access context, then move each AuricWell workflow onto the shared services with regression coverage for both frontends. Preserve useful new functionality and its acceptance cases while relocating it into the shared layer.

Inspect migration/application state before retiring any parallel storage. Do not delete tables or existing records as an architectural shortcut. Synthetic tests now demonstrate shared organization/client persistence, bidirectional model-level edit visibility, AuricWell stale-write rejection, atomic links and reviewed prototype conversion. They do not cover a deployed full-suite frontend using every shared EHR workflow.

Docker is not required. Migration 1509 adds canonical organization/client foreign-key links; migration 1510 adds the optional shared staff identity link. Migration 1511 adds the user product boundary and EHR-only status; migration 1512 adds canonical appointment links and origin/location columns. These migrations have only been applied to disposable test databases; production migration state and backups must be reviewed before rollout.
