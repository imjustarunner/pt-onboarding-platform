# Clinical encounters and video disconnection

Private offices keep a permanent tenant-specific URL, but each provider-ended encounter gets a fresh media session and artifact scope. Departure, browser closure, and heartbeat expiry do not authorize admitting a replacement client. A provider may explicitly add an intended couples/family participant to an ongoing encounter with an admitted participant. Clients may share materials; treatment-plan selection remains provider-controlled.

Apply migration `1531_clinical_encounter_security.sql` after `1530_tenant_office_session_workspace.sql`. Finish existing calls using the previous deployment before rollout. Untracked legacy media sessions cannot be reopened through the new clinical path; create a fresh counseling session if a preexisting scheduled session already has legacy media credentials. Existing authorized provider archives remain readable. They are retained rather than being silently migrated into an automatic deletion policy.

These migrations live in `database/migrations/` and use the **main** `DB_*` connection, alongside the existing office and counseling session tables. `migrate-clinical` targets `database/clinical_migrations/` using `CLINICAL_DB_*` and will not create these tables. From `backend/`, on an otherwise up-to-date database, run the following in order, then restart the backend:

```sh
npm run migrate -- --migration=1530
npm run migrate -- --migration=1531
```

The runner skips migrations already recorded as successful. The security startup gate deliberately refuses to start when these required tables are missing; bypassing it would not repair the schema. A missing `VONAGE_VIDEO_CALLBACK_SECRET` is a separate feature configuration issue and does not block general backend startup.

Configure the Vonage application's **Session Monitoring** callback to the backend's HTTPS `/api/clinical-video/events` endpoint. Enable signed callbacks and put the same secret in the backend secret manager as `VONAGE_VIDEO_CALLBACK_SECRET`. `VONAGE_APPLICATION_ID` must match the callback's project/application. The handler checks HS256 signatures, token age, exact raw-body SHA-256, and project identity. It processes connection-created, connection-destroyed, and session-destroyed events, including connections without published streams. See [Vonage session monitoring](https://developer.vonage.com/en/video/guides/session-monitoring) and [signed callbacks](https://developer.vonage.com/en/opentok/guides/secure-callbacks).

In the current dashboard, open Applications → Edit the application → Video capability → Session Monitoring. Older Video dashboards expose this under Account → Project → Session Monitoring → Configure. Enabling the signature-secret field generates a secret; use that same value in `backend/.env` for local development and the GitHub Actions repository secret `VONAGE_VIDEO_CALLBACK_SECRET` for deployment (or an existing Cloud Run Secret Manager binding). This is not the API secret or the SMS signature secret. Vonage documents that configuration updates may take up to 30 minutes. Localhost alone cannot receive Vonage callbacks; the callback URL must reach the backend handling that environment's sessions.

Clinical video refuses to open without monitoring configuration, and admission waits for a signed provider connection event. Ending first commits access revocation, then requests server-side disconnections. Failed disconnections remain pending and are retried every 15 seconds. New tokens expire after 60 seconds. The room stays locked until token windows close and a signed session-destroyed event confirms an empty room after that window. Callback delivery delays therefore delay reopening; the UI must not report completion prematurely. Monitor pending endings and callback failures. Callbacks and the retry scheduler must remain reachable/running in the deployed infrastructure; an idle Cloud Run instance must not be the only mechanism relied upon for scheduled work.

The provider's admission-to-departure duration and the monitored media duration are separate fields. Media durations merge overlapping connections for one visit. IP addresses retain their collection source (`direct_peer`, `verified_google_lb`, or `unverified_proxy`); configure the existing trusted ingress evidence policy before treating a forwarded IP as verified.

Clinical staff routes require verified application MFA even while enrollment is optional elsewhere and when the initial login used Google. They reuse the existing Account security enrollment, verification, recovery, session revocation and remembered-device controls. AuricWell staff entry uses its existing verified MFA and practice permissions. Scoped client invitation tokens remain restricted to their session. The clinical staff gate disallows impersonation/demo access.

Artifact reads, writes, browser download requests, admissions, ending, and connection events write metadata to the existing append-only `security_evidence` store. Clinical text, photos, PDF content, and credentials are excluded. Browser download requests are intent, not proof of saving or reading a file. Reads and artifact writes fail closed if their durable audit cannot be written. Keep the existing independent audit-log retention and database privileges configured; database triggers alone cannot constrain a database owner.

## Clinical session retention

Temporary check-in photos are cleared on departure/end/dismissal and by scheduled cleanup after expiry or abandoned waiting. Durable session artifacts default to **no automatic deletion**. Authorized tenant administrators can set an approved artifact retention period through `PUT /api/clinical-session-security/:agencyId/retention` with `{ "artifactDays": 3650, "confirmAutomaticDeletion": true }`; the number is an example, not a legal retention recommendation. Use `{ "artifactDays": null }` to disable automatic deletion. GET on the same route returns the effective policy. MFA and tenant-admin access are required.

`PUT /api/clinical-session-security/:agencyId/encounters/:kind/:sessionId/:generation/hold` accepts `{ "legalHold": true }` to protect an encounter from automatic deletion. Holds, policy changes, and deletion counts are audited. Cleanup only deletes the new workspace artifacts for finalized encounters past their configured period, without a hold. Attendance/audit records, existing clinical notes, transcripts, and legacy archives keep their existing retention rules. Backup, versioned-object, and retained-log lifecycles need separate infrastructure configuration; this job does not claim to delete those copies.

Local verification uses synthetic data only: `node backend/src/scripts/testClinicalSessionLocal.js` starts a disposable native MySQL server on a private temporary socket, applies the migrations, checks admission concurrency, successive-patient isolation, failed disconnections, callback ordering, retention/holds, and audit immutability, then removes the database. Set `CLINICAL_TEST_MYSQLD` if MySQL is installed outside the default Homebrew path. Before clinical rollout, also run a live two-device Vonage check with a camera-off subscriber, a failed-disconnect retry, callback interruption, a late/reused token, and successive patients across two tenants. No production migration, vendor configuration, or live clinical call was performed by these local tests.
