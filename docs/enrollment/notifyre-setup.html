Activate client notifications with Notifyre

Prepared October 17, 2026. Client Campaign 1 will use Notifyre. Staff messaging stays on its existing Vonage route. No live texts were sent during implementation.

What is ready

Portal email aliases created and accepted by Google Workspace

  • portal@auricwell.com — clinical enrollment, with the agency identified and replies directed to agency support.
  • portal@nextleveluplcc.com — Next Level Up tutoring enrollment.
  • School enrollment identifies the agency, SchoolCareBridge for school coordination, and AuricWell for the clinical portal.
  • Families get portal sign-in and an emailed password-setup option at enrollment completion.

1. Create the API token

In Notifyre, open Settings → Developer → API Tokens and create the integration token. Store it as the backend secret NOTIFYRE_API_TOKEN. Do not paste the token into a website form, commit it to Git, or send it in ordinary chat.

2. Create the signed webhook

Open Settings → Developer → Webhooks → New. Subscribe to sms_received and sms_sent. Use this backend endpoint:

https://onboarding-backend-378990906760.us-west3.run.app/api/notifyre/webhook

Click Reveal for the endpoint secret. Store it as NOTIFYRE_WEBHOOK_SECRET. This differs from the API token. The app validates the signature and timestamp, routes replies, records STOP, and processes delivery receipts.

3. Supply Campaign 1’s approved details

These details are not passwords and can be shared for configuration:

  • Actual Notifyre Campaign 1 ID and registered brand ID/name.
  • Exact linked sending number(s), including country code.
  • Approved use cases and the participating agency/brand scope.
  • Whether Notifyre handles STOP, START and HELP responses.
  • The existing app campaign and number being replaced, so prior opt-outs can be preserved.

The app requires tenant-owned sender registrations. An approved umbrella arrangement must be confirmed before mapping independent agencies to one campaign. A BAA does not replace the campaign approval, number linking, or recipient consent checks.

Activation sequence

  1. Deploy the code and database migration 1642_notifyre_webhook_receipts.sql.
  2. Add the two Notifyre secrets and set NOTIFYRE_CLIENT_CAMPAIGN_ID to the actual approved ID. Keep NOTIFYRE_ENABLED=false while configuring.
  3. Review Campaign 1 sender mappings and explicitly migrate prior opt-outs before replacing a campaign ID. Existing signed consent must cover the same brand and message purposes; it is not broadened automatically.
  4. Verify signed webhook delivery, STOP/HELP handling, sender branding and delivery receipts with a designated consenting test recipient.
  5. Enable NOTIFYRE_ENABLED=true after those checks. Other campaigns keep their current transport.

Read-only verification command: node backend/src/scripts/checkNotifyreReadiness.js. The example settings are in backend/.env.notifyre.example.

Insurance reminders

The existing secure upload task handles missing, replaced, waived and reviewed cards. Medicaid-only coverage is exempt; commercial coverage requires front and back images, including a commercial secondary policy. Missing cards remain outstanding after enrollment. Main now requires staff review before sending an insurance-card follow-up; the enrollment update preserves that policy and requires the same guardian’s signed all-service-email choice. Scheduling-only and declined choices do not authorize insurance follow-up. There is no additional automatic reminder worker to enable. Card uploads and OCR do not establish verified coverage or benefits.

Guardian invitation recovery

Migration 1643_co_guardian_invite_delivery.sql records delivery attempts and the submitting parent. Immediate send failures are visible at completion and in Guardian invitations. Structured permanent bounce reports are checked every five minutes, independently of AI inbox processing. The parent receives an agency/AuricWell notice linking to the portal, where they can correct the address and resend. Resending invalidates the old link. If the parent cannot be notified, the system creates a support follow-up.

An email service accepting a message does not prove the recipient saw it. Silent spam filtering or an incorrect address that belongs to a real person cannot be detected as a bounce. School invitations retain their existing staff-managed sending policy.

Historical audit: 19 pending invitations; 18 lack a recorded submitting account. Older records need a specific invitation/client reference and review before notifying a parent. No historical patient messages were sent during this work.
